The Goal Isn't Fewer AI Intents

Intent proliferation is a symptom, not the disease. What it actually signals about how you're thinking about conversational AI product design — and what to focus on instead.

Justin Yurasits · Draft — not for publication

The proliferation pattern

At some point in the development of almost every conversational AI product, the same thing happens: the intent list gets long. What started as ten intents becomes thirty, then eighty, then a spreadsheet nobody wants to open. Teams respond by calling this a problem and setting a goal to reduce the count.

This is the wrong response — not because intent count doesn't matter, but because treating reduction as the goal misidentifies what the count is actually telling you.

Intent proliferation is a symptom. It usually signals one or more of the following: unclear boundaries between what the system is supposed to handle and what it isn't, insufficient context-awareness that forces you to disambiguate at the routing layer, or a system designed around discrete task-handling rather than continuous understanding. Reducing count without addressing the underlying cause produces a different kind of mess — fewer intents that each try to do too much, and a system that fails less obviously but more often.

Why count is a proxy metric

Metrics earn their place by tracking something that matters. Intent count tracks the size of your routing taxonomy. That's not nothing — a taxonomy that's grown to 400 intents for a task-focused assistant is a signal worth attending to. But count doesn't tell you whether your system handles user goals well, whether it recovers gracefully from ambiguity, or whether users are getting what they need.

Teams that optimize for count reduction tend to end up with one of two failure modes:

  1. Merged intents that collapse distinct behaviors — "get schedule" and "get schedule for next week" become one intent, the system handles the unqualified case fine, and fails silently on the time-qualified one because the prompt template wasn't designed for it.
  2. Broad intents that shift complexity downstream — "construction query" becomes a catch-all that routes to a handler with its own internal disambiguation logic, reproducing the routing problem one layer deeper in the stack.

Neither of these is better than a larger intent list that's well-structured. What matters is whether the taxonomy accurately reflects the space of user goals you're handling and whether each intent maps to behavior that actually serves those goals.

The routing model fallacy

A deeper issue behind both of these failure modes is treating conversational AI routing as a classification problem. Traditional NLU systems classified utterances into intents and dispatched to handlers. That model made sense when the handlers were rigid rule-based flows. It makes less sense when the handlers are language models that can reason about context — but many teams carry the classification mental model forward anyway.

Here's what a typical intent configuration looks like in a system following this pattern:

# Intent configuration — anti-pattern example
# Intents proliferate because disambiguation happens at the routing layer

intents:
  - name: get_schedule
    description: "User asks about project schedule"

  - name: get_schedule_specific_task
    description: "User asks about a specific task in the schedule"

  - name: get_schedule_specific_task_delayed
    description: "User asks about a delayed specific task"

  - name: get_schedule_next_week
    description: "User asks about next week's schedule"

  - name: get_schedule_next_week_specific_phase
    description: "User asks about a specific phase next week"

# This continues. The router is doing work the LLM handler could do itself.

The problem here isn't the number of intents — it's that each intent represents a distinction the LLM handler could make on its own if the system provided adequate context. The router is acting as a disambiguation layer for a system that doesn't need one.

A better model

A more useful framing is to think about intent routing as scope management, not classification. The question isn't "which handler should process this utterance" but rather "what does this utterance need to be handled well, and does this system have that capability?"

Two models for intent routing. On the left: classification routes to N handlers; edge cases produce new intents. On the right: scope check decides in-or-out; the LLM handles disambiguation within scope.

In the scope management model, the routing layer answers one question: is this request within the scope of what this system is designed to handle? If yes, the request goes to a capable handler with the context it needs. If no, the system declines gracefully and explains what it can help with.

Disambiguation — figuring out exactly what the user means within a given scope — is left to the LLM handler, which is better equipped for it than a classifier anyway. This doesn't eliminate the need for routing structure, but it changes what that structure is for.

Practical implications

Concretely, this means a few things when designing or reviewing a conversational AI system:

  • Define scope before you define intents. What is this system actually for? The answer to that question should be legible to users, not just to developers. If your scope definition is fuzzy, your intents will be too.
  • Push disambiguation downstream. If you find yourself creating intents to handle variations of the same underlying goal, ask whether the handler could handle that variation itself given adequate context — history, session state, retrieved data.
  • Measure what matters. Task completion rate, user recovery from failure, and fallback frequency tell you more about system quality than intent count. Count is an input to those metrics, not a substitute for them.
  • Distinguish scope failures from handling failures. When the system fails, determine whether it failed because the request was out of scope and the system didn't recognize it, or because the request was in scope and the handler produced the wrong output. These require different fixes.

None of this means intent architecture doesn't matter. Clear, well-scoped intent definitions make systems easier to reason about, test, and maintain. The goal is a well-designed intent taxonomy, not a small one — and those are different targets.
